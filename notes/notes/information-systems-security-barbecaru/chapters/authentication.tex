\chapter[]{Authentication}
\section{Authentication basics}

\paragraph{Identification vs. Authentication}
Identification answers the question \textit{"Who are you?"} (e.g., providing a username), while authentication answers \textit{"Are you really who you claim to be?"} (e.g., providing a password).
A common shorthand for authentication is \textbf{AuthN}, which is distinct from authorization (\textbf{AuthZ}).

\paragraph{Authentication Factors}
We can authenticate a user through different mechanisms, commonly referred to as \textbf{factors}:
\begin{itemize}
    \item \textbf{Knowledge}: something only the user knows (e.g., password, PIN, security question).
    \item \textbf{Ownership}: something only the user has (e.g., hardware token, smart card, smartphone).
    \item \textbf{Inherence}: something the user is (e.g., a biometric characteristic such as a fingerprint, voice, or iris scan).
\end{itemize}
\textbf{Multi-factor authentication (MFA)} occurs when different mechanisms are combined. For instance, \textbf{2-factor authentication (2FA)} typically combines knowledge and ownership.

\paragraph{Advantages and Disadvantages of Factors}
All factors come with inherent trade-offs:
\begin{itemize}
    \item \textbf{Knowledge}: Passwords are easy to implement and can be delegated to other people if necessary. However, they are highly susceptible to theft, guessing, or phishing. Furthermore, human memory is limited; enforcing complex, frequently changing passwords often leads to insecure practices, like writing them down or reusing them across platforms.
    \item \textbf{Ownership}: Physical tokens or devices are secure against remote guessing, but they risk unauthorized usage if unlocked, physical theft, or cloning.
    \item \textbf{Inherence}: Biometrics offer high convenience, but they risk counterfeiting and raise severe privacy concerns. The most critical flaw of inherence is that it is \textbf{non-revocable}: if your password is stolen, you can easily change it; if your fingerprint data is compromised, it is compromised for life. For this reason, inherence should ideally be restricted to \textbf{local} authentication, acting as a mechanism to unlock a device's secure enclave (like FaceID on a smartphone) rather than transmitting biometric data to a remote server.
\end{itemize}

\section{Passwords}
Passwords remain the most widespread authentication mechanism. Typically, a server maintains a database linking users to their passwords.

If a server stores passwords in \textbf{plaintext}, it poses a high security risk. If an attacker breaches the server, the credentials of \textbf{all} users are compromised. Furthermore, if the password is transmitted over an unencrypted channel, it is vulnerable to network sniffing.

To mitigate database breaches, servers should store a \textbf{cryptographic hash} of the password using a one-way hash function. During login, the client transmits the plaintext password (ideally over a secure channel like TLS). The server calculates the hash of this received password and compares it to the hash stored in the database. If they match, authentication succeeds.

\paragraph{The Dictionary Attack and Rainbow Tables}
Even when passwords are hashed, they remain vulnerable to offline attacks if the database is leaked. Hypothesis: an attacker breaches the server and steals the database of hashed passwords, but does not know the plaintext passwords.

Because cryptographic hashes cannot be mathematically inverted, the attacker performs a \textbf{dictionary attack}. They take a massive list of common words, phrases, and leaked passwords, and pre-compute the hash for every single entry. Attackers often store these pre-computed hashes in massive databases called \textbf{Rainbow Tables}, which may take months to generate. Once built, the attacker simply searches their table for the stolen hashes. If a match is found, the underlying password is revealed.

\paragraph{Defending with Salts}
The standard defense against dictionary attacks and Rainbow Tables is the use of a \textbf{salt}. A salt is a long, cryptographically secure random string. Instead of just hashing the password, the server generates a unique salt for \textit{each individual user}. The server appends this salt to the password before hashing it: $H(\text{password} + \text{salt})$. Both the resulting hash and the plaintext salt are stored in the database.

\textbf{How salts defeat pre-computation:} Because every user has a unique, random salt, two users with the exact same password will have completely different hashes. This renders the attacker's pre-computed Rainbow Table entirely useless. To crack the passwords, the attacker would be forced to compute a completely new dictionary table for \textit{every single user} based on their specific salt, making the attack computationally infeasible.

\paragraph{Verification Workflow with a Salt}
When a user attempts to log in, the verifier performs the following operations:
\begin{enumerate}
    \item Receives the User ID (UID) and the plaintext password from the user.
    \item Looks up the UID in the database to retrieve the user's unique \textbf{salt} and the stored \textbf{hash}.
    \item Computes the hash of the provided password combined with the retrieved salt: $H(\text{password} + \text{salt})$.
    \item Compares this newly computed hash with the stored hash. If they match exactly, the password is correct; otherwise, authentication fails.
\end{enumerate}


\section{Challenge-Response Authentication (CRA)}
While passwords are widely used, they have a critical flaw: the secret (even if hashed) must be transmitted across the communication channel. To avoid exchanging sensitive data directly, modern authentication methods leverage cryptography.

The \textbf{Challenge-Response Authentication (CRA)} mechanism operates on a simple premise: the user claims an identity, and the verifier presents a "challenge" that the user must solve. Because the solution requires a secret stored locally (like a symmetric or asymmetric key), the user proves possession of the secret without ever transmitting it over the network.

For CRA to be secure, two main properties must hold:
\begin{itemize}
    \item The challenge must be \textbf{non-repeatable} (typically a random \textit{nonce} - number used once). If challenges were predictable or reused, an attacker could sniff a valid response and use it for subsequent authentication attempts (a \textbf{replay attack}).
    \item The cryptographic function used to compute the response must be \textbf{non-invertible} (e.g., a cryptographic hash function). Otherwise, an attacker could intercept the response and reverse-engineer the locally stored secret.
\end{itemize}

Challenge-Response protocols can be implemented using either symmetric or asymmetric cryptography.

\subsection{Symmetric Challenge-Response}
In this method, both the user and the server share a secret key ($K_{ID}$) linked to the user's ID. The workflow is as follows:
\begin{enumerate}
    \item The user sends their ID to the server.
    \item The server replies with a random challenge (a nonce).
    \item The user computes a response by applying a function (often a fast cryptographic hash like SHA-256 or SHA-3) to the challenge and their shared secret key.
    \item The user sends this computed response to the server.
    \item The server, possessing its own copy of the shared key, computes the same function on the challenge. If the server's result matches the user's response, authentication succeeds.
\end{enumerate}

The primary vulnerability of symmetric CRA is that the verifier (server) must store the shared keys ($K_{ID}$) in \textbf{cleartext}. Consequently, if the server's database is breached, the attacker gains the keys for all users, completely compromising the system.

\subsection{Asymmetric Challenge-Response}
This method eliminates the need for a shared secret by utilizing a pair of asymmetric keys (public and private) owned by the user. There are two primary variations:

\paragraph{Method 1: Digital Signature}
\begin{enumerate}
    \item The user sends their ID, their \textbf{public key}, and a digital certificate validating that key.
    \item The server verifies the certificate's validity with a Certificate Authority (CA).
    \item The server generates and sends a random challenge (nonce) to the user.
    \item The user \textbf{signs} the challenge using their \textbf{private key} and sends the signature back.
    \item The server verifies the signature using the user's previously provided public key.
\end{enumerate}

\addfigure[Asymmetric challenge-response schema with digital signature]{/png/CRA-as1.png}{0.8}

\paragraph{Method 2: Decryption}
\begin{enumerate}
    \item The user sends their ID, their \textbf{public key}, and a digital certificate.
    \item The server verifies the certificate.
    \item The server generates a random challenge (nonce), \textbf{encrypts} it using the user's \textbf{public key}, and sends the ciphertext to the user.
    \item The user \textbf{decrypts} the challenge using their \textbf{private key}.
    \item The user sends the decrypted (plaintext) challenge back to the server.
    \item The server verifies that the received response matches the original challenge it generated.
\end{enumerate}

\addfigure[Asymmetric challenge-response schema with encryption]{/png/CRA-as2.png}{0.8}

\paragraph{Advantages and Disadvantages}
Asymmetric CRA is widely considered the strongest form of authentication. Because the verifier only stores or receives public keys, a server breach does not compromise user credentials. This robust security model is why asymmetric CRA is the foundation of peer authentication in major protocols like IPsec, SSH, and TLS.

However, the method has some drawbacks:
\begin{itemize}
    \item \textbf{Performance overhead}: Asymmetric cryptography operations are computationally heavier and slower than symmetric ones.
    \item \textbf{PKI Dependency}: It relies heavily on Public Key Infrastructure (PKI) and third-party Certificate Authorities (CAs) to verify that a certificate is valid and has not been revoked.
    \item \textbf{Hardware requirements}: The claimant must possess a device capable of securely storing a private key and performing complex asymmetric mathematical operations.
\end{itemize}


\section{One-Time Passwords (OTPs)}
A \textbf{One-Time Password (OTP)} is an authentication string that is valid for only a single login session or transaction. From the user's perspective, this method requires no manual cryptographic calculations. It offers a significant security upgrade over static passwords because it is inherently immune to \textbf{sniffing and replay attacks}: even if an attacker intercepts the password in transit, it becomes useless the moment it is used.

However, standard OTPs still present several challenges and disadvantages:
\begin{itemize}
    \item \textbf{Single-use limitation}: The password is valid for just one authentication attempt; every subsequent login requires a completely new password.
    \item \textbf{Susceptibility to Real-Time MITM}: While immune to offline replay attacks, OTPs are still vulnerable to active Man-in-the-Middle (MITM) attacks or real-time phishing. If an attacker intercepts the OTP and uses it instantly (before the legitimate user does), they can hijack the session.
    \item \textbf{Password exhaustion}: If using a pre-generated list, the user will eventually run out of passwords and need a new batch.
    \item \textbf{Usability}: OTPs are typically random alphanumeric strings designed to resist guessing, making them difficult and tedious for users to type manually.
\end{itemize}

\paragraph{OTP Provisioning Methods}
To solve the problem of generating and distributing these passwords, the industry relies on two primary provisioning solutions:
\begin{itemize}
    \item \textbf{Hardware Authenticators (Crypto Tokens)}: Dedicated physical devices (like RSA SecurID) that generate trusted OTPs on demand. Historically, verifiers distributed physical "password cards" (e.g., scratch cards or grid cards) containing a printed list of OTPs, but these are now obsolete due to physical security risks and exhaustion.
    \item \textbf{Software Authenticators}: An app running on a smart device (like a smartphone). The device computes the OTP locally. While highly convenient, this requires the device to be secure; if the smartphone is infected with malware, the attacker could silently generate an OTP and authenticate in the background.
\end{itemize}

\subsection{Time-Based One-Time Passwords (TOTP)}
To eliminate the need to distribute lists of passwords, modern systems predominantly use \textbf{Time-Based OTPs (TOTP)}. In this model, the user's device and the server share a secret seed. The OTP is generated on the fly by computing a cryptographic hash of this shared secret combined with the \textbf{current time}.

While TOTPs solve the exhaustion and distribution problems, they introduce new technical challenges:
\begin{itemize}
    \item \textbf{Device dependency and security}: The user must possess a computing device (hardware token or smartphone) to generate the real-time password. As mentioned, running authenticator apps on a general-purpose smartphone exposes the credential generation process to mobile malware.
    \item \textbf{Time synchronization and drift}: Because generating the OTP relies on the current time, both the user's device and the server must be synchronized. To accommodate slight clock differences and network delays, the protocol defines a \textbf{time-step} (or time-slot), typically 30 or 60 seconds. The verifier server usually accepts the OTP for the current time-step ($T$), as well as the immediately preceding ($T-1$) and following ($T+1$) time-steps.
    \item \textbf{Time manipulation attacks}: An attacker can exploit the time dependency by desynchronizing the victim's device. For example, smartphones often synchronize their clocks via the mobile network or Network Time Protocol (NTP). An attacker could deploy a rogue base station (IMSI catcher) or spoof NTP packets within a local radius (10-15 meters) to feed the device a fake time. This could cause the device to generate future OTPs, which the attacker can harvest and use later.
\end{itemize}
